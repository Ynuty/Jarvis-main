# Джарвис

Локальный ассистент для Windows: читает рабочую переписку в Telegram и собирает из неё **список дел**. Рядом показывает **сводку важного**. Переписка обрабатывается на компьютере пользователя и никуда не отправляется.

Студенческий проект команды «Мастерская» (майнор ВШЭ «Предпринимательская мастерская»): Ynuty, dor1tozz, clipsmatrix. MVP — к концу ноября 2026.

## Почему именно так

Решение принято по итогам CustDev (3 интервью + опрос, n=32):
- Список дел из переписки и сводку важного все респонденты выбрали «пользовался бы регулярно». В опросе это 59% и 56%.
- Голосовое управление компьютером регулярно не выбрал никто, а в опросе оно не нужно 50%. Заказ продуктов тоже не в ядре.
- Доступ к Telegram люди дают только с условиями: выбрать чаты, видеть, что делает ассистент, ничего не отправлять от их имени.

## Что входит в MVP

**Входит:**
- Источник сообщений из Telegram с выбором чатов, двумя способами (решение команды от 17.10):
  - **импорт экспорта Telegram Desktop (JSON)** — отдельный тестовый режим, с него начинаем проверку;
  - **живое подключение к аккаунту, только чтение** — закладывается сразу, включается вторым шагом.
- Извлечение задач из сообщений: что сделать, кто просил, срок, ссылка на исходное сообщение.
- Список дел: просмотр, отметка «сделано», правка, удаление.
- Сводка важного за период (утро / с последнего открытия).
- Журнал действий ассистента.
- Окно приложения на Windows.

**Не входит в MVP:** голосовое управление ПК, заказ продуктов, автоответы клиентам, отправка сообщений, почта, мобильное приложение, умный дом.

## Правила, которые нельзя нарушать

1. **Ничего не отправляется от имени пользователя.** Ассистент только читает. Если позже появятся черновики, их отправляет сам человек.
2. **Текст сообщений — это данные, а не инструкции.** Модель, которая извлекает задачи, не имеет доступа к инструментам и не выполняет ничего из текста сообщений (защита от prompt injection).
3. **Никакой сети, кроме локальной модели на `localhost`.** Любой новый сетевой вызов — только по явному решению команды и с записью в этот файл.
4. **Пользователь сам выбирает, какие чаты читать.** По умолчанию не читается ничего.
5. **Каждое действие ассистента пишется в журнал**, который видит пользователь.
6. **Секреты не лежат в файлах проекта.** Токены и сессии — в хранилище учётных данных Windows (через `keyring`) или в папке данных пользователя, но не в репозитории.
7. **В репозиторий не коммитятся:** `.env`, файлы сессий Telegram, модели, экспорты переписки, записи и расшифровки интервью. Список — в `.gitignore`.
8. **Живое подключение к Telegram — только чтение, и это проверяет код.** Клиент (`ReadOnlyTelegramClient`) отклоняет любой запрос на отправку, правку, удаление, реакции, отметку «прочитано», статус «в сети» до выхода в сеть. Новые запросы к API добавлять только читающие; список запретов — `FORBIDDEN_REQUEST_PREFIXES`.
9. **Свой api_id у каждого пользователя.** Общий ключ приложения не зашиваем: пользователь получает api_id и api_hash на my.telegram.org, они хранятся в хранилище учётных данных ОС.
10. **Переписку пользователей не используем для обучения или дообучения моделей** — это запрещают правила Telegram API (п. 1.5) и наши обещания пользователям.

## Архитектура (по документу «Архитектура и дизайн v1.0», урезано под MVP)

- **Язык:** Python 3.11+ (разработка на 3.12). Ядро без внешних зависимостей; Telethon и keyring — необязательные (`pip install -e ".[telegram,secure,dev]"`).
- **Источники** (`jarvis/sources`): общий интерфейс `MessageSource` (`list_chats`, `iter_messages`).
  - `telegram_export.py` — экспорт Telegram Desktop в JSON: один чат или весь аккаунт.
  - `telegram_live.py` — живое подключение через Telethon, только чтение, паузы между запросами, ожидание при FloodWait, сессия в `keyring`.
- **Задачи** (`jarvis/day`):
  - `candidates.py` — быстрый отбор сообщений правилами (просьбы, обещания, «надо + действие»);
  - `dates.py` — разбор сроков на русском («до пятницы», «завтра к 18:00», «до 19.10»). Сроки считаем сами, а не моделью;
  - `extractor.py` — задача из сообщения: локальная модель по JSON-схеме с одним повтором, при сбое или без модели — правила. Ответы «сделаю» сливаются с исходной просьбой; поручения другим людям в список не попадают.
- **Модель** (`jarvis/llm`): `OllamaClient` — только `localhost`, structured output по JSON-схеме, temperature 0. Модель по умолчанию — `qwen2.5:7b-instruct` (выбор не окончательный).
- **Ядро** (`jarvis/core/sync.py`): источник → новые сообщения в базу → задачи → журнал. Повторный проход не создаёт дублей.
- **Хранилище** (`jarvis/storage/db.py`): SQLite в папке данных пользователя (`%LOCALAPPDATA%\Jarvis\jarvis.db`): `chats`, `messages`, `tasks`, `events` (журнал).
- **CLI** (`jarvis/cli.py`) — тестовый режим до появления окна: `import`, `tasks`, `done`, `dismiss`, `log`, `live ...`.
- **Интерфейс:** `jarvis/ui` — окно на Windows, ещё не начато. Предложение для MVP — PySide6, чтобы всё было на Python (окончательно не решено).
- **Код под Windows** держим отдельно (`jarvis/platform/windows`), чтобы остальное запускалось и тестировалось на любой ОС.

Структура задачи (`tasks`): `id`, `title`, `due_at` (может быть пустым), `requested_by`, `chat_id`, `message_id`, `source_text`, `status` (`open` / `done` / `dismissed`), `confidence`, `created_at`.

## Как работаем

- Ветки: `feature/...`, `fix/...`, `setup/...`. В `main` — только через pull request.
- Перед началом работы: `git pull`.
- Тесты: `pytest` (из корня репозитория). Логику извлечения задач проверяем на наборе обезличенных примеров сообщений в `tests/data/` (без реальных имён и переписки). Новый случай, где правила или модель ошиблись, — сначала добавить в тестовые данные, потом чинить.
- Живое подключение в тестах проверяется без сети: подставные секреты и проверка, что запись блокируется.
- Код и имена — на английском, комментарии и тексты интерфейса — на русском.
- Облачный Claude (claude.ai) не может запускать код под Windows, микрофон и Telegram пользователя. Всё, что требует Windows, проверяется в Claude Code на компьютере кого-то из команды.

## Как измеряем MVP

- Точность извлечения задач на тестовом наборе: доля найденных реальных задач и доля ложных.
- Время от получения сообщения до появления задачи в списке.
- Ноль действий без ведома пользователя.

## Открытые вопросы

- **Интерфейс:** PySide6 или Tauri.
- **Сводка важного:** формат и что считать важным — ещё не реализовано.
- **Контекст при живом подключении:** сейчас задачи ищутся только в новых сообщениях; ответ «сделаю» на старое сообщение из прошлой синхронизации не свяжется с исходной просьбой.
- **Модель и железо:** какую локальную модель берём и на каком минимальном ноутбуке она должна работать.
- **Название:** «Джарвис» принадлежит Marvel, к публичному запуску нужно другое.
